# 2026-08-06 -- Semantic diff: align repeated siblings, summarize array edits

Design and implementation session. The Symbols tab over-reports structured-config diffs; this note
pins down why, designs the fix in three parts, validates the design with a prototype run against the
real revisions from PR #409 -- and records the implementation, which landed the same day and
reproduces the validated output through the production `diffEntities` path.

## The problem, measured

PR #409's `.config/cspell.jsonc` change is semantically three edits: `"lezer"` added to the
`dictionaries` array, one definition object added to `dictionaryDefinitions`, and two words added to
`words`. The current engine reports **21 rows** for it:

```text
[added]    dictionaryDefinitions.name#7          @ new L51
[added]    dictionaryDefinitions.path#7          @ new L52
[added]    dictionaryDefinitions.description#7   @ new L53
[modified] dictionaries                          @ new L5
[modified] dictionaryDefinitions                 @ new L23
[modified] dictionaryDefinitions.name#2 .. description#6   (15 rows)
[modified] words                                 @ new L98
```

Two failures are visible at once:

- **A positional-identity cascade.** Properties inside array elements are disambiguated with `#n`
  ordinal suffixes (`dictionaryDefinitions.name#2`), and the matcher's first phase trusts that
  qualified name as identity. Inserting the lezer object at array index 1 shifts every later
  definition's ordinal, so old `name#2` (licenses) is claimed by new `name#2` (lezer) and reported
  as modified -- fifteen times over. Worse, the three `added` rows land on the ordinal that fell off
  the end (the _last_ definition object), so click-to-jump navigates to the wrong lines.
- **Opaque scalar arrays.** `dictionaries` and `words` are arrays of strings; strings are not
  entities, so each array reports one bare `modified` with no indication of what changed or where.

The report a reviewer actually wants is three rows:

1. `dictionaries` -- array 13 -> 14, `"lezer"` inserted at index 9
2. `dictionaryDefinitions` -- array 6 -> 7, one object inserted at index 1
3. `words` -- array 167 -> 169, `"ciphertext"` at index 9 and `"nullserve"` at index 158

The goal generalizes past this file: reduce the number of hierarchical elements in the list by
reporting each change once, at the highest node that fully describes it.

## Root cause: identity by ordinal position

`disambiguate()` in `extract-entities.ts` numbers name collisions in document order, and
`matchEntities()` phase 1 keys on the resulting qualified name. That makes sibling identity
_positional_, and positional identity cascades on insertion -- the same pathology line-based diffs
have, reintroduced one level up. The prior art this engine is modeled on does not have this problem:
sem, difftastic, and diffsitter all _align_ sibling sequences by content when names repeat, rather
than trusting an ordinal label. Our flat name-keyed matcher skips that alignment step; the fix is to
add it, not to abandon the three-phase design.

The same cascade applies anywhere siblings share a name: JSON/YAML arrays of objects, repeated
markdown headings, function overloads. The fix below is language-agnostic for that reason.

## Design

### Part 1 -- occurrence alignment (matcher, language-agnostic)

Phase 1 of `matchEntities()` stops keying on the suffixed qualified name and instead groups both
sides by **(kind, base path)**, where the base path strips every `#n` suffix. Singleton groups --
the overwhelmingly common case -- behave exactly as today. For multi-occurrence groups, the two
occurrence sequences are aligned:

1. **LCS on `contentHash`** -- hash-identical occurrences pair up preserving order. A pair whose
   content is identical is the same entity, however far an earlier insertion shifted it; it reports
   nothing, and its ranges stay honest for click-to-jump.
2. **Remainder paired in order** -- an occurrence edited in place keeps its position relative to its
   unedited siblings, so leftover old and new occurrences zip in order and report `modified` when
   `ownContentHash` differs.
3. **Leftovers** are genuine adds/deletes and fall through to phases 2 and 3 unchanged.

On the cspell file this alone collapses 21 rows to 6: the three bogus-modified groups vanish, and
the three `added` rows attach to the lezer object's actual lines.

Display names keep the `#n` suffix for now -- identity no longer depends on the label, so improving
the label (for example `dictionaryDefinitions[1].name`) becomes a pure presentation decision for a
later pass.

### Part 2 -- sequence detail on array-valued properties (structured formats)

Array _elements_ stay non-entities -- a 169-word list must not eat the 2000-entity file budget --
but the property that owns the array gains an element-level fingerprint list at extraction time:
`contentHash` (comments already excluded by the signature walk), a short text preview, and the
element's range. In Lezer terms: for a JSON `Property` whose value child is an `Array`, fingerprint
each named value child; YAML block/flow sequences follow the same contract later via their own spec
entry.

When the matcher pairs an entity with itself and both sides carry fingerprints, it runs LCS over the
element hashes and attaches a structured `detail` to the `modified` change:

```ts
interface SequenceEdit {
  type: 'inserted' | 'deleted'
  index: number
  preview: string
  startLine: number
  endLine: number
}

interface SequenceDetail {
  lengthBefore: number
  lengthAfter: number
  edits: readonly SequenceEdit[]
}
```

The Symbols tab renders the detail under the row -- `array 13 -> 14`, then one line per edit, each
clickable to its line. Rendered edits are capped (first ~8 plus `+n more`); the detail computation
itself is skipped past a size guard (~2000 elements a side) and the row falls back to today's bare
`modified`.

### Part 3 -- rollup

An added or deleted entity row whose span sits inside an inserted or deleted element already
reported by an ancestor's sequence detail is suppressed -- the element edit _is_ the report.
Containment is checked by source offsets plus base-path prefix, not lines alone. This is what turns
"object inserted at index 1" into one line instead of one line plus a row per key inside the new
object. Only inserted/deleted element spans suppress; an element merely modified in place keeps its
nested leaf rows, because those name the precise key that changed.

## Validated outcome

A prototype of all three parts (scratchpad, ~200 lines reusing `extractEntities`,
`computeSignature`, and the app's JSON parser) run against the real before/after blobs of
`.config/cspell.jsonc` from PR #409:

<!-- cSpell:ignore leze -->

```text
[modified] key dictionaries @ L5
    array 13 -> 14
    inserted at index 9: "lezer" (L15)
[modified] key dictionaryDefinitions @ L23
    array 6 -> 7
    inserted at index 1: { "name": "lezer", "path": "dictionaries/leze... (L25)
[modified] key words @ L98
    array 167 -> 169
    inserted at index 9: "ciphertext" (L109)
    inserted at index 158: "nullserve" (L261)
```

Exactly the three-row report specified above, index for index. LCS is O(n \* m) on 32-bit hashes;
the largest array here (169 words) costs ~45k cell operations, microseconds in practice, and the
size guard bounds the pathological case.

## Decisions

- Fix identity in the **matcher**, not extraction: alignment is a diff-time question, and keeping
  `disambiguate()` untouched leaves single-file extraction deterministic.
- Elements are **fingerprints, not entities**: sequence membership is data on the owning property,
  so entity counts, the matcher's phase structure, and the UI's row model all survive unchanged.
- LCS reports a reordered element as delete + insert. Move detection (pairing leftover equal hashes
  across positions) is deferred until a real diff misreads badly enough to justify it.
- An element edited in place currently surfaces as delete + insert at the same index; coalescing
  that pair into a `changed` edit is a presentation follow-up.

## Known adjacent nit (not in scope)

`@lezer/json` has no comment support, so JSONC comments parse as error nodes. The signature walk
drops `Comment` node types but not error nodes, meaning a comment-only edit still flags the
enclosing property as `modified`. Options when it graduates to in-scope: strip comments before
parsing `.jsonc`, or adopt a JSONC-capable grammar.

## Implementation (landed 2026-08-06)

All three parts shipped, with two deviations from the plan's sketch, both toward the matcher:

- Rollup lives in `match-entities.ts`, not `diff-entities.ts` -- suppression runs _before_ the
  rename phases, so an entity inside a deleted element cannot be fuzzily paired with something
  unrelated across the file. Covered occurrences also stay out of the in-order zip, which would
  otherwise pair one deleted object's keys with another inserted object's.
- The pure algorithms (common-end strip, LCS, element diff) live in a new `sequence-alignment.ts`;
  `match-entities.ts` keeps only the phase orchestration.

Where things landed: types in `entity.ts` (`EntitySpan`, `SequenceElement`, `SequenceDetail`,
optional `EntityChange.detail`); element fingerprinting in `extract-entities.ts` behind
`EntitySpec.resolveSequence`, implemented for JSON arrays in `languages/structured.ts`; alignment
and sequence diff in `sequence-alignment.ts` + `match-entities.ts`; edit rendering in
`sequence-edit-rows.tsx` under each row in `symbol-changes-list.tsx`. The regression suite covers
the cascade, the zip, detail indexes, entity-owned pair silence, rollup, and the distilled cspell
pair end-to-end; the real PR #409 blobs reproduce the three-row report through production code.

## Dogfood round (same day)

Reading this PR's own Symbols tab found a second cascade the design missed: locals inside anonymous
callbacks. `scope: 'top-level'` was checked against the entity frame stack, and an arrow passed to
`test()` never becomes a frame, so the consts inside it looked module-level -- six spurious `added`
rows on `extract-entities.test.ts`. Fixed twice over: a new `anonymousScopeProp` marks closure node
types (JS/TS, Go, Rust, PHP) so the walker counts them as executable scope, and vitest-style calls
with a literal title (`test`, `it`, `describe`, `bench`, member and curried forms) are now `test`
entities. The file now reports its two added tests by title plus the one real module constant.
