# 2026-08-22 -- investigation and plan

Session summary: investigated merge-queue options for the recurring `bun.lock` conflict pile-up and
wrote the project plan. No implementation yet.

## Work completed

- Ruled out GitHub's native merge queue (org-owned repos only; also rejects conflicted PRs, so it
  never solved this problem) and external queue apps (Kodiak and its peers) per the build-in-repo
  preference.
- Confirmed upstream status: bun does not resolve lockfile conflict markers
  ([oven-sh/bun#17717](https://github.com/oven-sh/bun/issues/17717), open).
- Ran the conflict experiment locally on bun 1.3.11 (two branches adding alphabetically adjacent
  packages; details and numbers in [plan.md](./plan.md)). Established that bare `bun install` on a
  conflicted lockfile silently re-resolves from scratch and floats every range, while take-theirs +
  `bun install --lockfile-only` yields exactly the PR's delta, byte-identical across runs, passing
  `--frozen-lockfile`.
- Confirmed Depot CI workflows can be dispatched externally (CLI + API) and that the repo already
  has working label-triggered bot workflows and App-token push patterns to copy.

## Decisions made

- Three-phase shape: Depot updater workflow -> Renovate automerge -> GitHub App queue on Cloudflare
  Workers (Durable Object per base branch, updater as the muscle).
- Resolution recipe takes main's lockfile (`--theirs`) before regenerating -- preserves main's
  resolutions, re-resolves only the PR delta.
