### feat(revision.city): select the files that a review covers

`selectReviewFiles` picks the files of a pull request that a review covers, in GitHub's order. It
leaves out lockfiles, generated files, and removed files with no note. It lists each file with no
text diff, a diff longer than 1500 lines, or a diff over the review size limit, so that the check
run can show what was not reviewed. The files to review fit in 700,000 bytes, because a Cloudflare
Workflow keeps at most 1 MiB for each step result. The list of files that it cannot review stops
after 65,000 characters, because the check run cuts its text there. Nothing calls it yet.

### fix(revision.city): bind the review database by its id

The `DB` binding now names the `revision-city` D1 database by its id. Without the id,
`wrangler deploy` must find or create the database itself. The deploy token has no D1 permission for
that, so each production deploy since #810 stopped with an error.

### fix(revision.city): retry when OpenRouter puts a provider error inside an answer

When a provider accepts a request and then fails, OpenRouter can answer 200 with the error in the
first choice, next to a partial answer. The review used the partial answer as the model's answer. So
a cut-off answer failed to parse, or, if it held a complete JSON object, passed as a clean review
and was saved. Now the review treats this answer as a temporary failure and sends the request again,
as it does for an error at the top level of the answer.

## 2026-10-12

### feat(revision.city): review chunks in batches and scope saved results

`reviewPullRequest` now has three parts that a Workflow can call one batch at a time.
`planChunkReviews` lists the chunk reviews, `reviewChunks` runs a batch of them, and
`summarizeChunkReviews` adds up the outcomes. When a chunk review fails because a call failed, its
outcome says whether a new attempt can succeed. After an OpenRouter error that is not temporary,
such as a bad key, a new attempt cannot succeed. Each saved chunk review now has a scope, such as
one GitHub App installation. Thus a saved result never shows that another installation reviewed the
same code. `mise run review` uses the scope `local`.

### feat(revision.city): limit findings per answer and do not review diffs over 1500 lines

One model answer now adds at most 20 findings to a review, and they are the most severe ones. A
title longer than 200 characters or a body longer than 3000 characters is cut short. A suggestion
longer than 3000 characters is dropped, because a cut suggestion would replace the lines with broken
code. By default, a file whose diff has more than 1500 lines is not reviewed. A caller can change
this limit with the `maxPatchLinesPerFile` option. `fileReviewStatus` tells why a file is not
reviewed: skipped by design, no text diff, or a diff that is too large.

### feat(revision.city): review pull requests as a GitHub App

revision.city now reviews pull requests as a GitHub App. GitHub's `pull_request` webhook reaches
`/api/github/webhook`, which starts one `ReviewWorkflow` instance for each review. The Workflow runs
each review step with retries, gets an installation token for the pull request's repository, and
keeps chunk reviews in D1. The Workflow and D1 bindings are on the production worker only, so the
webhook answers 503 on the dev worker and the previews. Only `DavidJFelix/DavidJFelix` gets reviews
until billing exists.

### feat(revision.city): add a GitHub REST helper

revision.city has a small GitHub REST client. It sends the API version and user agent headers, an
optional token, and an optional JSON body. It checks each response against a zod schema, and a
failed request throws a `GitHubApiError` that has the HTTP status. The client reads list endpoints
page by page, up to a page limit. It lists the files of a pull request in this way, up to GitHub's
limit of 3000 files. Nothing uses the client yet.

### feat(revision.city): get GitHub App installation tokens

`createInstallationTokenSource` signs an RS256 JWT with the app's private key and exchanges it for
an installation token. The token can reach only one repository, with `checks: write`,
`contents: read`, and `pull_requests: write`. Calls share one token until 5 minutes before it
expires. The private key can be PKCS#1, as GitHub generates it, or PKCS#8. Nothing uses the tokens
yet.

### feat(revision.city): retry OpenRouter requests and support tool calls

When a request fails for a temporary reason, the OpenRouter client tries it up to two more times,
after 2 and then 8 seconds. Temporary reasons are a network error, a 408, 429, 500, 502, 503, or 504
status, and an error object in a 200 response. Other failures, such as a bad key or a response the
client cannot read, do not cause a retry. An `OpenRouterError` says whether its cause is temporary.
The client now sends a list of chat messages, can offer tools, and returns the model's tool calls.
The reviewers do not use tools yet.

A reply could quote JSON before the real answer. If an object inside that JSON had a `findings`
list, the answer parser took that object as the answer. The engine then saved the wrong findings for
the chunk review. The parser now tries an object inside another object only after all outer objects.
An answer that the model wraps in another object still parses.

### feat(revision.city): post reviews and check runs to GitHub

`createCheckRun` and `completeCheckRun` start and finish the Revision City check on a commit.
`postReview` posts at most 50 of the reported findings, most severe first, as one review of inline
comments. It reads the fingerprints in the app's earlier review comments, and skips a finding that
the app already posted on the same path and line. GitHub refuses the whole review when it cannot
place one inline comment. Then `postReview` posts a review without inline comments, and its body
lists the findings. `removeLabel` takes a label off a pull request. Nothing calls these functions
yet.

### feat(revision.city): load a snapshot of a commit's file tree

`loadRepositorySnapshot` reads the recursive Git tree of one commit from GitHub. It reads a blob
when a caller first asks for it, and keeps the blob for later calls. After a failed read, the next
call tries again. When GitHub truncates the tree, it returns nothing, because then a missing path
does not prove that a file does not exist. `readsStillMatch` tells whether files that were read from
one snapshot are unchanged in a newer one. The reviewers do not use the snapshot yet; a later change
gives them tools that read files from it.

### feat(revision.city): write the text of review comments and the check run

A finding's comment starts with a hidden fingerprint of the reviewer, path, title, and body. A later
run uses it to tell which findings an earlier run posted. The comment shows the severity, the
reviewer, the title, a suggestion block when the finding has one, and the body. The review body
lists the findings when GitHub does not accept them as inline comments. The check run output gives
the counts and the cost. It also lists the findings, the failed chunk reviews, and the files that
were not reviewed, cut to fit GitHub's limit.

Model text and file paths can come from the pull request's author. So the text breaks mentions,
issue references, HTML, and the model's own suggestion blocks. A file path stays inside its code
span, even when the path has backticks. GitHub links go through redirect.github.com, so they do not
show in the timelines of other issues. Nothing posts this text yet.

### feat(revision.city): add tools that read the pull request head for a reviewer

Three tools read files from a snapshot of the pull request's head commit. `read_file` returns
numbered lines, at most 300 for each call. `list_directory` lists at most 200 entries of a
directory. `read_definition` returns a function, class, type, or other named item that
`extractEntities` finds. The tools refuse binary files and files over 1 MB. Each call that looks up
a path records the path and the Git object id at that path. If nothing is at the path, the id is
empty. The reviewers do not call the tools yet.

### feat(revision.city): run a pull request review as Workflow steps

`runReview` runs one review as steps that a Cloudflare Workflow can retry and resume. It removes the
review label when the label started the review, and it creates the Revision City check run on the
head commit. It lists the files and reviews the chunks in batches of 3 chunk reviews, 6 batches at a
time, so that each step result stays under the 1 MiB limit. A review covers at most 150 chunks. Then
it posts the review and completes the check run. A batch runs again when a tool fails, or when a
model call fails for a temporary reason. The saved answers make the new attempt pay only for the
reviews that failed. When the pull request closes or gets a new head during the review, nothing
posts and the check run ends as neutral. Nothing starts a review run yet.

### feat(revision.city): let reviewers read files through tools

With a snapshot of the pull request's head commit, a reviewer can call `read_file`,
`list_directory`, and `read_definition` before it answers. The prompt asks it to read only the code
that a possible problem depends on. One chunk review has at most 4 rounds of tool calls, 6 calls in
a round, and 48,000 characters of tool output. A saved answer records each path that its tools
looked up, including directories and paths that do not exist. A later run uses the saved answer only
if none of those paths changed. If a model call or a tool fails, the chunk review fails, but the
cost of its earlier model calls still counts. The prompt also tells reviewers to treat instructions
in the diff and the files as text to review. It says that an empty suggestion deletes the lines.
`mise run review` loads the snapshot, so its model must support tool calls. It also lists the files
that it does not review because they have no text diff or are too large.

### feat(revision.city): check GitHub webhooks and decide which events start a review

`handleReviewWebhook` checks the HMAC signature of a GitHub App webhook against its body. It starts
a review Workflow only for a `pull_request` event that the trigger rules accept. A review starts
when a pull request in an allowed repository opens, gets a push, reopens, or becomes ready for
review. It does not start for a draft, or when the author is a bot or has no access to the
repository. Adding the `Revision City` label to an open pull request starts a review in these cases
too. A repeated delivery of one event does not start a second review. Until billing exists, only
this repository is allowed. No route serves the handler yet.

### fix(revision.city): read the answer after other JSON in a model reply

A model can quote other JSON, for example from the diff, before its answer. The answer parser took
the first JSON object in the reply, so such a reply failed its chunk review. The parser now takes
the first object that has a `findings` list.

### fix(revision.city): recover the diffs worker from a truncated cached script and from a deploy

In Firefox 155, the diffs highlight worker failed on each page load, and the refetch in the failure
report returned 200. A HAR of the failure shows the cause. The browser asked for
`/assets/worker-<hash>.js` with `If-None-Match`, the server answered 304, and Firefox used its
cached copy. That copy had only 256 KiB of the compressed response, which is 733,088 of the 836,769
characters in the script. The truncated script does not parse, so the worker failed. Because asset
responses have `max-age=0, must-revalidate`, each page load revalidated the same copy, got 304
again, and failed again. The report did not show this because the refetch used `cache: 'no-store'`
and cancelled the body. The Firefox behavior comes from the HAR only; a search found no Mozilla bug
that describes it.

The refetch now uses `cache: 'reload'` and reads the full body. A `reload` request ignores the
cached copy and puts the full response in the cache. The report also gives the size of the body that
the refetch read. The result of the refetch then decides what the page does:

- **200**: the cache now holds a complete script, so the page starts the worker pool again. The
  review UI holds the viewer until the second start ends, because a viewer that mounts without the
  pool does not use it later.
- **404**: a deploy removed the script that this page asks for. The page reloads once to get the
  names of the current scripts. A mark in session storage for that script URL stops a second reload.
- **Any other result**: the diff renders on the main thread, as before.

A lazy chunk from an old deploy has the same problem. On `vite:preloadError`, the page reads the
chunk URL from the error message and asks the server for it. If the server answers 404, the page
reloads once, with the same session storage mark. Safari puts no URL in the message, so Safari does
not reload.

## 2026-10-09

### fix(revision.city): report why a diffs worker fails instead of logging `[object Event]`

A failed diffs highlight worker reached Sentry as `Worker error: [object Event] [object Object]` and
`Error: [object Event]`. Both came from `@pierre/diffs` 1.5.1: its pool logged the raw `error` event
and the pool's internal worker record, then turned the event into an `Error` with `String(event)`.
In Chromium, the `Worker` gets an event with no message when the browser cannot fetch the worker
script (an error status or a network error). A script that throws gives an `ErrorEvent` with a
message. In a classic worker, which builds use, a script that is not JavaScript also throws.

`@pierre/diffs` moves to 1.5.2, which adds an `onWorkerError` pool option. When the option is set,
the pool gives the event to the option instead of logging the raw objects. The release also catches
its own failed initialization, which was the unhandled `Error: [object Event]`.

revision.city's handler writes one report for each distinct failure on a page and raises it with
`reportError`, so Sentry's `onerror` handler records a real message. For a load failure, the handler
fetches the worker script again and reports the status and content type the server returns, or the
network error. It also reports how long the page was open and `navigator.onLine`. For an uncaught
error, it reports the message and the script location.

`workerFactory` now constructs the worker from its `?worker&url` import, so the handler knows which
URL to fetch. Vite's own rule for the worker type stays the same: a module worker in dev and a
classic worker in builds.

The PR workflow in `CONTRIBUTING.md` and the comments rule in `AGENTS.md` now ask authors to run the
`comment-review` skill over the diff before each push that changes prose. `comment-style.md` names
the two findings that the first review of this change raised. They are a claim that the code does
not support and old wording in a touched comment.

### fix(revision.city): render a diff when the diffs highlight workers fail to start

The `@pierre/diffs` highlight worker pool can fail to initialize, for example when the worker script
at `/assets/worker-<hash>.js` returns 404 or hits a network error. In that case, the diff viewer
never rendered, and the page stayed on its loading status. The review UI showed the viewer only
after the pool reported `managerState: 'initialized'`. A failed pool goes back to `'waiting'` and
sets `workersFailed`, so it never got there. This gate stopped the library's fallback to
highlighting on the main thread.

The gate now also opens when the pool reports `workersFailed`, and the viewer then renders without
the pool (`disableWorkerPool`). Opening the gate alone was not enough. A viewer that still used the
failed pool called `setRenderOptions` to set its theme. In 1.5.1 and 1.5.2, that call starts a new
initialization even after a failure. Each attempt requested the worker script again and hid the
viewer until it failed, so the diff flickered and the requests did not stop. Without the pool, the
viewer highlights on the main thread with the theme the reader picked.

A Playwright test, `worker-fallback.e2e.test.ts`, answers the worker script with 404 and the diff
request with a fixture patch. It pins the core count, so the pool always starts three workers. It
then checks that the file renders with highlighted tokens and that each pool worker loads the script
exactly once.

### feat(revision.city): add the pull request review engine

First step toward revision.city reviewing pull requests as a GitHub App. The engine splits each
reviewable file's patch into chunks and asks three reviewers (security, correctness, comments) about
each chunk through OpenRouter. It maps the findings back to file lines, reports `medium` and above,
and fails on `high` and above or when a chunk review fails. A store saves each chunk's answer under
a hash of the model, reviewer, system prompt, and chunk text. Its D1 table is a drizzle schema, and
`mise run db:generate` writes the migrations. Once the GitHub App uses the D1 store, a re-run pays
only for chunks that changed or whose answer was not saved. Lines are labeled inside the chunk, so a
chunk that only moves in the file, for example after a rebase, keeps its saved answer.
`mise run review -- owner/repo#123` prints the findings for a pull request; it keeps answers in
memory, so each run pays for every chunk. Nothing posts to GitHub yet.

## 2026-10-08

### chore(web-apps): upgrade Panda CSS to v2

`@pandacss/dev` moves from 1.12.1 to 2.1.1 in the workspace catalog, the release that replaces
Panda's TypeScript extractor with a Rust engine. The styling API is unchanged, so no source edits
were needed in any of the nine Panda apps: their `css()` calls, patterns, recipes, and `styled` JSX
props compile as before, and the PostCSS plugin and `panda codegen` keep working from the existing
configs.

Three breaking changes reached this repo:

- v1 bundled `@pandacss/preset-base` and `@pandacss/preset-panda` inside `@pandacss/dev` and applied
  both by default; v2 ships them as standalone packages and applies only the presets a config lists.
  Every Panda app now declares both packages (pinned in the catalog at the same version as
  `@pandacss/dev`, as the upgrade guide requires for every `@pandacss/*` package) and lists both in
  `presets`, including the two apps that previously relied on the implicit default and had lost
  every preset token and condition.
- v2 writes the generated runtime as `index.js` where v1 wrote `index.mjs`. The two SvelteKit apps
  (alchemy-state-viewer and monicandavid.com) reach the output through a `#styled-system/*` subpath
  import in package.json that named the old extension, so their builds could not resolve any
  styled-system module until the import map was pointed at `index.js`. Local checkouts should run
  `panda codegen --clean` once, since v2 does not delete the stale v1 files.
- v2 loads the app's tsconfig to follow path aliases, and pkg.dog's tsconfig references files that
  `nuxt prepare` generates, so its `prepare` script now runs `nuxt prepare` before `panda codegen`.

v2 also narrows the `prose` size token in `@pandacss/preset-panda` from `65ch` to `60ch`, which
djf.io's prose recipe and the forzamonica.com root layout use for their measure.
