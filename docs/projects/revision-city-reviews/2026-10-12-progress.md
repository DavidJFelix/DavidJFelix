## Work completed

- **Tools** (`tool-loop.ts`, `review-tools.ts`, `repository-snapshot.ts`). Each reviewer can call
  `read_file`, `list_directory`, and `read_definition` on the head commit, through GitHub's tree and
  blob APIs. One chunk review gets at most 4 tool rounds, 6 calls in each round, and 48,000
  characters of tool output. A saved result records each path that its tools read, with the path's
  git object id. A later run uses the result only while those ids do not change.
- **Webhook** (`/api/github/webhook`, `webhook.ts`). The route verifies the HMAC-SHA256 signature
  over the raw body and checks the allowlist and the trigger rules. Then it starts one
  `ReviewWorkflow` instance. The instance id comes from the repository, the pull request, and the
  pull request's update time. An automatic run also adds the head commit. So a delivery that GitHub
  sends again starts nothing new, and a later event on the same head starts a new review. Without
  the secret or the binding, as on the dev worker and the previews, the route answers 503.
- **Workflow** (`review-workflow.ts`, `run-review.ts`). The `start` step creates the check run while
  the pull request is open and still has the event's head. A label run takes the current head
  instead. Each `review N of M` step runs 3 chunk reviews (1 chunk for the 3 reviewers), 6 steps at
  a time. A step result at the finding limits is about 0.72 MiB, under Cloudflare's 1 MiB limit for
  each step result. When a tool fails, or a model call fails for a temporary reason, the Workflow
  runs the step again, at most 3 more times. The saved answers make the new attempt pay only for the
  chunk reviews that failed. An OpenRouter error that is not temporary, such as a bad key or an
  unexpected response, does not cause a new attempt. When no new attempt follows, the check run
  reports a failed chunk review. Then `post review` and `complete check run` run. When a step fails
  after its retries, `report failure` fails the check run.
- **Installation tokens** (`github-app-auth.ts`). An RS256 JWT, signed with the app's private key,
  gets a token for the one repository with `checks: write`, `contents: read`, and
  `pull_requests: write`.
- **Posting** (`publish-review.ts`, `review-markdown.ts`). One review posts at most 50 new inline
  comments. When GitHub refuses a line (422), the review lists the findings in its body instead. The
  check run lists every finding and failed chunk review, and each file that the size limits or a
  missing text diff kept from review. It cuts its text at 65,000 characters.
- **Configuration** (`wrangler.toml`). The `ReviewWorkflow` and D1 bindings are on the production
  worker only.
- **Fixes found while splitting.** OpenRouter can answer 200 with a provider error inside the
  answer, and the client now tries again (#806). The worker types were stale, so #807 regenerated
  them. With 6 chunk reviews in a step, a step result at the finding limits was about 1.4 MiB, so a
  step now runs 3. After a batch step fails on its last attempt, no more batch steps start.
- A local `vite preview` run checked the route. An unsigned request got 401, and a signed `ping` got
  `ignored`. A signed `pull_request` started an instance, and the same delivery again was a
  duplicate.

## Decisions

- Tool loop in phase 2 (David chose it). `read_definition` uses the Lezer extractor of the Symbols
  tab, not SCIP. A SCIP index needs a build with the language toolchain for each head commit, and a
  Worker has no toolchain.
- The tools read through the GitHub REST API, not a Cloudflare Container. A tree read lists the head
  commit, and a blob read gets one file.
- Check run conclusions: `failure` on a finding at `high` or above, a failed chunk review, or a
  failed step. `neutral` when the pull request closed or got a new head during the review. `success`
  otherwise.
- The `Revision City` label asks for a review of any open pull request, so drafts, bot pull
  requests, and outside authors can still get one on request.
- The 1,500-line limit for each file is a constant in code (David asked). A manual review request
  can go over it later.
- The D1 binding gets a database id, the same as monicandavid.com, so the shared deploy token needs
  no D1 permission.
- Posted model text and file paths are untrusted. A zero-width space breaks mentions, issue
  references, HTML, and entities in them. Links to github.com go through redirect.github.com, so
  they do not show in the timeline of the linked issue. The finding's body goes last, so a fence in
  it cannot take in the suggestion.
- Known limits, kept for now:
  - A label run can overlap the automatic run on the same head, and then comments can repeat.
  - Findings that GitHub refused as inline comments have no fingerprint, so a later run posts them
    again.
  - When the `start` step retries after GitHub made the check run, the first check run stays in
    progress.
  - A retried review step reports only the cost of its last attempt.
